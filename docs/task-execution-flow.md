# 任务执行流程

发布基线：`release_20261109` 的 `f7cc63280e4c03703f164216ba340c31935b4fc0`。

## 部署

- SQLite 在仓库初始化时自动新增 `agentgate_run_events` 表及索引。
- MySQL/TDSQL 已有数据库先执行 `scripts/upgrade/20261103/20261103_run_events.sql`，再部署后端和前端。脚本仅建表，可重复执行。
- 新装 MySQL/TDSQL 使用 `scripts/sql/init.sql`，已经包含新表。
- 不回填历史日志，不修改任务快照。回滚应用时可保留新增表。

## 记录与查看

单任务详情的“执行流程”页签以表格展示提交任务、等待执行、准备智能体、执行样本、评估与汇总五项，打分与结果保存、报告汇总合并展示。表格列出状态、开始/结束时间和覆盖时间区间；展开阶段行查看原始明细的耗时、异常及样本／轮次／评估器信息。正在执行和未恢复异常的阶段默认展开，已完成阶段收起；重试错误保留在明细中。Run、去重的请求 ID 和 BJS 批次号统一放在顶部“关联信息”，不同重试批次保留派发次数。BJS 作业 ID 不在页面展示。A/B 任务详情展开“执行流程（A/B）”，选择实验侧，关联信息随之切换。

一次阶段执行一条记录，开始插入，结束更新；重试新增记录并保留失败尝试。请求接收和校验阶段使用 `request_id`，任务创建后通过任务的关联日志一同查询。请求尚未创建任务就失败时，记录只有请求 ID；响应头 `X-Execution-Request-Id` 可供运维在表中追踪。表内 `id` 同时是阶段操作 ID。

表格上方展示任务全流程的开始时间、结束时间和总耗时，取自 `run` 阶段，包含调度等待和 Pod 准备等时间，不累加各阶段耗时。运行中实时展示已运行时长；中断或终态但未采集结束时间时显示未知，历史任务没有全流程记录时显示未采集。

阶段覆盖请求接收/校验/创建、预约等待、并发额度等待、派发及重试、Worker 接收和环境初始化、样本目标调用和重试、Trace 获取、评估器执行、样本结果保存、报告汇总、任务终态。

行内 ChatABC（基础／工作流）和云虾额外记录“创建被测智能体 Pod”“等待被测智能体 Pod 健康检查通过”，云虾启用健康检查后固定等待时另记“健康检查后的固定等待”。每阶段开始即落库，结束记录耗时；创建失败、健康检查超时等异常保留错误码和脱敏说明。创建阶段包含创建接口的既有重试，健康检查阶段包含既有轮询和等待；不改变超时、重试和启动顺序。多样本复用同一个 Run 的 Pod，不为每个样本重复记录 Pod 启动。本阶段是被测智能体 Pod 的应用健康检查，不是 BJS 执行 Pod 的 Kubernetes 探针；行外模拟任务不生成这些阶段。

查询接口：`GET /api/runs/{run_id}/events?offset=0&limit=100`；最大每页 200 条，沿用当前用户的团队权限。页面分批读取完整日志后统一汇总，避免第一分页之外的异常和批次号遗漏；每个节点的明细按 20 条分页。页面打开后每 5 秒刷新，切走或页面隐藏时停止；可以暂停和手动刷新。任一日志分页读取失败保留上次完整内容，不改变任务状态。

## 时间与异常口径

- 数据库存 UTC，页面按浏览器本地时区显示；阶段完成记录固定耗时，运行阶段显示已运行时间。
- 不累加并行阶段耗时；评估器给出低分仍是执行完成，只有执行异常记为失败。
- 引擎取得 Trace 后将其已有轮次/节点时间写入日志。模拟 Trace 不生成真实节点耗时。没有上游数据时不猜测内部节点；本版不增加上游实时事件接入。
- 服务已有恢复检查发现任务超过期限时，将未结束阶段标为 `interrupted`。该行 `ended_at` 是检查发现时间，不是真实节点结束时间，界面明确显示“结束时间未知”；不会把发现时间冒充实际执行耗时。
- 用户取消与执行失败分别记录。未结束的并发阶段被任务终止时标记中断，而非伪造为正常完成。
- 异常不保存请求体、模型提示词或堆栈；对凭据键、Bearer 和 URL 脱敏并限制长度。日志写入失败只写入现有服务日志，不替代原始业务结果。
- SQLite/MySQL 日志在各阶段独立事务提交，不随随后业务操作回滚。删除任务时删除关联 Run 的日志；没有任务的请求日志暂按现有数据库运维流程清理，本版不增加后台清理进程。

## 运维查询

MySQL/TDSQL 使用 `run_id` 或 `request_id` 查询，按 `started_at` 排序；开始/结束时间、耗时、状态、错误码和异常说明均是独立列。样本、轮次、评估器和尝试次数保存在 `payload` JSON 文本中。API 查询通过哈希索引定位任务，避免扫描全表。

BJS 受理成功后，派发阶段的 `payload` 额外保存 `bjs_job_id`（提交的 `jobId`）和 `bjs_batch_number`（返回的 `onlineBatchSeqNum`）；详情页展开顶部“关联信息”即可取得批次号，再到 BJS 平台查询。页面隐藏作业 ID，后台仍使用它提交任务并保存在日志中，也用于区分不同作业的同名批次。复用现有 `payload` 字段，无需新增数据库列。未返回有效字符串批次号时不补造；提交失败和历史记录没有该批次号。只保存这两个标识，不保存 BJS 完整响应。受理成功不代表已开始执行，仍需结合“等待 Worker 接收”和 BJS 平台状态判断。

“关联信息”同时展示 `agentId` 和被测 Pod 的关联表：`pod_task_id` 是创建接口实际传入的短 `taskId`，`pod_name` 是接口返回的 `agentName`（沿用适配器中的 Pod／实例名称，不推断 Kubernetes 资源名）。任务创建时在全流程日志记录 `agent_id`；ChatABC 和云虾创建 Pod 前记录 `agent_id`、`pod_task_id`，名称成功返回后立即更新同一记录，因此健康检查失败仍可查看名称。创建失败时名称为空。以上字段都保存在现有 `payload` 中，无需 SQL 升级。重复记录去重，同一短 taskId 对应的不同实例名称分别保留。历史任务的 agentId 从固定任务快照读取，未采集的 Pod 标识不从 Run ID 猜测或补造。行外任务不创建行内 Pod，也不生成这类标识。

没有日志的旧任务展示“未采集”。记录失败本身会降低诊断完整性，可搜索服务日志中的 `Execution log persistence failed` 排查表是否升级及数据库连接问题。
